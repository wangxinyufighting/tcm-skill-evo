# v6：技能培养与检验

> 历史说明：本页记录 v6 的配对试用流程。当前默认是 [v7 多方案对比与技能迭代](knowledge_exploration_v7.md)，工作技能直接进入常规候选，配对试用不再是必要环节。以下命令和默认值不是当前推荐配置。

本页对应协议 `knowledge-evolution-v6`。LLM 参数不更新，训练对象是带版本、来源和试用反馈的技能库。

核心改变不是降低正式技能门槛，而是让未成熟技能先获得真实的训练期试用机会：单例启发的局部规则可以先进入假设库，在后续病例中实际影响处方，再根据得失修订；不再要求它先获得多例“支持票”才能被使用。

## 1. 每一步做什么

1. 读取当前训练批次的完整 `desc_raw`。普通候选继续使用正式技能库和四类知识包；可复用旧运行的普通候选，但标明其历史策略来源。
2. 从此前步骤形成的可执行假设中，选择当前原文相关、适用的版本。此时不读取当前原方或得分。刚看完当前答案才提出的技能不能回头在同一步冒充预测。
3. 固定病例、知识包、正式库及激活结果，先写入 `practice_plans/`，再生成两臂：对照臂不加入该草稿；试验臂加入该草稿，或替换其指定的正式规则。
4. 两臂具有相同的病例原文、知识包和其余正式规则。草稿在试验臂中强制注入，避免被正式规则的召回名额挤掉；正式门控仍检验正常召回路径能否触发及获益。
5. 全部普通候选和试用候选生成完毕后，才向评分器揭晓当前原方。保存每个方案的处方、生成时理由、引用和多维评分。
6. 优化器读取当前与相关历史经验，包括试用失败、无变化、无效输出和适用性未知原因，提出新增、修订、合并或拆分。单例经验允许提出局部技能，不要求立即总结跨病证原则。
7. 定义合法且练习证据达到就绪条件的版本转入待验证库；冻结该版本，按预算进行新留出组门控。通过后才进入正式库。
8. 本步经验、技能库、版本关系和进度一起提交。传输或提交失败回滚本步；重跑复用已经冻结的试用计划，成功请求可走缓存。

普通训练候选和冻结评测仍只用正式库。未成熟版本只在明确标记的离线训练试验臂使用，不混入正式能力成绩。

## 2. 三类库及版本

| 库 | 内容 | 下一步 |
| --- | --- | --- |
| 假设库 | 单例局部经验、尚未获益的规则、失败版本、必要信息未知的想法、格式或定义待修订稿 | 合法且适用的草稿继续试用；其他条目保留并反馈原因，不自动丢弃 |
| 待验证库 | 达到练习就绪条件的冻结版本 | 独立门控；覆盖不足保持待验证，并继续未完成的无标签预筛 |
| 正式技能库 | 通过独立初筛及启用时的复核的版本 | 普通开方和冻结评测使用；新改动另建版本并重新检验 |

- `op=revise, revises=H编号, id=""` 修订工作版本。程序保留其底层 add/replace 目标关系；修订正式来源会绑定相应 R 规则。
- `op=add, parents=[H编号...]` 表示合并；多个 add 指向同一父版本表示拆分。`revision_reason` 说明改变及依据。
- 新版本保存父版本引用，但不继承父版本的试用分数或独立支持数。父版本历史继续保留；有可执行的新子版本时优先试用子版本，子版本正式通过后才归档直接父版本。
- 同一核心定义重复提出只合并来源，不清空失败记录，也不增加独立组数。开始试用或进入待验证后不原地改写规范化定义及其引用；实质改动需要新版本。
- 行为门控失败的原版本仍可在训练病例上试用，帮助寻找修订方向，但不能不改定义就反复抽新门控组碰运气。
- 删除正式规则不创造新技能，仍直接进入待验证队列并接受独立行为检验。

工作库是有界预算下的持续培养，不保证每个草稿每步都有机会，也不保证分数随病例数单调提高。

## 3. 试用选择及就绪条件

默认每步最多 `hypothesis_trial_budget=2` 个配对试用，即最多额外生成 4 个处方。最多预筛 `hypothesis_trial_scan_limit=8` 个假设-病例组合；已有正式规则的适用性检查、定义审核和门控调用另计。

选择只用当前批次原文、规则召回相关度和最久未检查顺序；不使用原方、候选成绩、未来练习病例或门控病例。基础必要事实未知时不执行该技能，但保存原因供修订。相同版本和相同规范化原文组不重复累计试用证据；失败和未知均不能通过重复 cid 稀释。

培养模式中的 `min_support` 含义已改变：它是进入待验证前的最少独立配对练习组数，不再是 LLM 判 supports 的票数。

进入待验证必须同时满足：

| 条件 | 当前实现 |
| --- | --- |
| 可执行定义 | 结构、来源 ID、原文锚点和定义审核通过；没有把必要患者事实误写成任务动作 |
| 最少练习 | 至少 `min_support=3` 个独立原文组有有效对照臂 |
| 观察到获益 | 至少一次试验臂 F1 高于对照臂 |
| 平均不退步 | 所有有效对照组的平均 `delta = F1(试验) - F1(对照)` 不小于 0，不能只取胜例 |
| 约束不恶化 | 上述组中 `risk_flags/citation_errors/anchor_errors/oov_count` 各自的总增量不大于 0 |
| 未被失败锁定 | 同一核心版本未曾行为门控失败；replace/delete 的正式目标版本没有变化 |

这是工程性的“值得进一步检验”条件，不是统计显著性或泛化证明。独立门控标准没有放宽：初筛仍要求有效触发组数、`min_delta=0.005`、`t_min=1.28` 和四项约束；启用复核时仍需非负收益和约束不恶化。

格式无效的试验臂按 F1=0 留在比较中，可能是负收益或零收益，不悄悄排除。无效对照臂的配对也保存，但不提供有效比较数。网络失败则中止并回滚，不作为技能失败样本。

`soft_f1_optimal`、症状覆盖、有据用药比例等仍完整记录并提供给优化器；当前晋升主指标仍是原方 F1，没有偷偷引入新的混合总分。

## 4. 审核问题修复

### 任务场景不再要求患者原文证明

程序提供固定的 `workflow_context`：当前任务就是依据病例与证据选药、比较依据及决定增删。病例不必写出“需要取舍候选药”。

- 纯任务场景的第 0 项可引用 workflow 文本；程序还会检查独立定义审核确实将其判为 `workflow_context`。
- 混合患者事实的第 0 项仍需病例原文引用；任务部分由程序场景提供，患者部分不能因此省略。
- 所有 `required_conditions`、患者分支和排除项仍用病例证据；不能以 workflow 引用替代缺失的症状、舌脉或证型。
- 必要事实未知仍不执行；技能保留等待合适病例或新版本，不把未知当作处方错误。

### 定义审核区分硬错误与建议

`issues` 显式区分 `blocking` 和 `advisory`。措辞建议、重复、部分重叠或“问题不突出”不再因出现于 issues 中就否决。

硬错误须给合法问题类型、精确字段和逐字引文；条件冲突或无条件执行分支的指控还须给关联字段及引文。找不到对应片段记 `invalid_definition_review`，不算行为失败。

审核提示明确：“若……则……”“替换时……”仍保留条件，不因它位于 `decision_steps` 就认定为无条件执行。必要项的角色分类和分支类型检查仍保留。LLM 仍可能误判；这里修复的是协议和证据校验，未声称消除了语义判断误差。

### 患者分支与过程分支分开

- `branches[].kind=patient`：条件由患者原文支持才注入对应动作；未知或矛盾只关闭该分支，不否决整个基础技能。
- `branches[].kind=procedure`：只允许候选药、证据或方案的操作性比较，作为带条件指令交给执行者，在生成时判断成立才执行。不是声称该条件已经成立。
- 省略 kind 的兼容输入仍按 patient 处理。定义审核阻止把患者症状或证型藏进 procedure。

### 修订操作不再误当正式替换

现在明确支持 `revise + revises=H编号`。旧式 `replace + id="" + revises=H编号` 在父版本存在时兼容归一化，记录在 `revision_normalizations`。带非空错误 R 编号的 replace 仍报错，不静默改成新增。

### 不再要求单例证明整套技能

默认培养模式不以观察性支持审核票数决定能否试用；直接比较实际执行该版本前后的输出。

保留的 `observe` 消融中，对比审核可给 `supported_parts` 和 `unverified_parts`，程序核验对应技能字段。提示明确只评价既定的原方一致性与知识约束，不以“尚非临床/因果证明”或“候选未逐字执行后来总结的完整步骤”作为唯一否决理由。局部支持不冒充全部分支已验证。

## 5. 数据、反馈与恢复

- 原始病例全文不截断、不回退到抽取症状。现有训练、门控、val/test 原文组隔离及历史曝光账本继续保留。
- `practice_plans/` 在两臂生成前固定版本、知识包、对照/试验激活、提示签名和计划签名。成功请求缓存与断点事务共同支持失败重跑。
- `steps/step_*.json` 的候选增加 `practice_arm` 和 `hypothesis_id`；`practice_trials` 引用两臂候选索引，保留得分、有效性及约束差值。
- `state.skill_libraries` 是权威状态；条目增加 `practice_observations`、`practice_screenings`、`parents`。断点检查练习来源、原文签名、版本一致性、配对知识包一致性、得分差和版本关系。
- 优化器优先看到当前试用反馈，即使两臂平分、没有普通偏好对，也可进入反思。历史摘要保留失败与未知；库变大时先省略非当前试用的库摘要，避免挤掉所有病例，仍不截断病例原文。
- 训练诊断新增 `practice_screened/practice_trials/practice_wins/practice_losses/practice_ties/hypothesis_blockers`。`rules=0` 可能伴随有效试用与版本改进，不能单独代表没有学习；也不能仅凭这些训练计数声称泛化提高。
- `complete=true` 仍只表示练习流结束，不保证所有假设成熟。最后一步新产生的草稿可能还没有后续试用机会。

培养实验按预算训练，不把门控、val/test 当作工作库的支持案例；独立门控有多次自适应选择风险，最终结论仍看冻结评测。

## 6. 复用 v5 的小实验

v6 的实现、提示和证据语义已经变化，不能在旧 v5 目录直接续跑。旧目录不改写。`--reuse_run` 只导入已提交普通候选和曝光来源，不自动继承旧技能、旧支持票或旧门控结果；v6 来源中的实验臂也不会被当成新的对照证据。

在项目根目录运行：

```bash
export DEEPSEEK_API_KEY=magpie
python scripts/evolve_knowledge.py train \
  --llm openai_compatible \
  --run_name knowledge_v6_pilot64 \
  --reuse_run "$PWD/runs/knowledge_v5_pilot64" \
  --set knowledge.learning_mode=cultivate \
  --set knowledge.n_practice=64 --set knowledge.batch=8 \
  --set knowledge.gate_size=4 --set knowledge.confirm_size=4 \
  --set knowledge.gate_candidate_limit=24 \
  --set knowledge.min_support=3 \
  --set knowledge.hypothesis_trial_budget=2 \
  --set knowledge.hypothesis_trial_scan_limit=8 \
  --set knowledge.pending_gate_budget=1 \
  --max_steps 4
```

原 `knowledge_v5_pilot64` 已提交的前 32 例普通候选可以回放；新的成对试用、反思、审核和可能发生的门控仍需要 API，不能把回放称为零调用训练。未迁移旧工作库，因此第一步重新形成假设，后续步骤才开始试用。

同一配置将 `--max_steps 4` 改为 `--max_steps 8`，会在该 v6 目录继续到总计 8 步，而非额外 8 步。先检查试用确实发生、理由与改动有效，再考虑扩量，不以“出现正式技能”作为调低门槛的目的。

```bash
python scripts/evolve_knowledge.py diagnose --run_dir runs/knowledge_v6_pilot64
```

`--replay_only` 只限制普通候选生成，新的技能配对试用仍会调用当前模型。`--collect_only` 同时关闭草稿试用、优化器和门控。`hypothesis_review_budget` 仅供 `learning_mode=observe` 使用。

## 7. 实现与验证边界

主要实现：`knowledge_cultivation.py` 负责无标签计划和配对试用，`knowledge_evolution.py` 组织训练及升级，`knowledge_lifecycle.py` 保存版本与证据，`knowledge_routing.py` 审核及路由，`knowledge_policy.py` 负责执行与反思提示，`knowledge_experience.py` 负责经验选择及回放隔离。

测试覆盖单例起步、有效/失败/平分/无效处方反馈、修订及合并拆分、任务引用边界、条件分支、门控失败锁、回滚恢复、历史候选不冒充当前对照、冻结评测不读草稿及状态污染检测。mock 测试只能验证这些工程行为，不能证明真实模型会持续改善、审核已被校准或处方具有临床有效性。
